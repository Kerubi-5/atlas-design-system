# Component guide

Import each module from `atlas-react-kit/<subpath>`. Primitives preserve the
underlying element or Radix props, including `className`, alongside their options.
Form helpers and `TableBodySkeleton` accept only their documented props. There is
no root component barrel.

For installation, see [README.md](./README.md); for styling and accessibility,
see [DESIGN_RULES.md](./DESIGN_RULES.md).

For LLM-assisted implementation of patterns this kit does not export, use
[COSS UI](https://coss.com/ui) as a reference before building a component from
scratch. Its Base UI catalog includes input groups, number fields, OTP fields,
drawers, and segmented controls. COSS is a separate library; its components
are not Atlas exports.

## Status

Components are **stable** unless listed here. Stable components change
through the deprecation policy in
[CONTRIBUTING.md](https://github.com/Kerubi-5/atlas-design-system/blob/main/CONTRIBUTING.md#deprecations).

**Beta** components may still change shape in a minor release, before and
after 1.0; they are exempt from semver, and the changelog calls out every
change: `accordion`, `avatar`, `breadcrumb`, `chart`, `dropdown-menu`,
`kanban`, `nav-link`, `page-header`, `pagination`, `period-stepper`,
`radio-group`, `skip-link`, `spinner`, `switch`.

## Styling parts

Every component takes `className` for its root and passes other HTML props
through to it. Where a part sits inside a component, a prop names it, and
each part carries a `data-slot` for parent selectors such as
`*:data-[slot=stat-tile-value]:text-2xl`.

## Forms

`TextFieldApi` is a structural interface, with no form library dependency:

```ts
type TextFieldApi = {
  name: string
  state: {
    value: string
    meta: {
      errors: (string | { message?: string } | undefined)[]
      isTouched?: boolean
    }
  }
  handleChange: (value: string) => void
  handleBlur: () => void
}
```

`FormTextField` accepts `field` and `label`; use `multiline` and `rows` for a
textarea, `inputType` for a specific input, and `showError={false}` to suppress
error text and invalid styling. `FormMarkdownField` uses the same `field` shape
for a Write / Preview GFM body. `FormSelectField`, `FormDatePickerField`, and
`FormDateTimePickerField` accept the same error meta shape.
`FormDatePickerField` takes a `Date` or `yyyy-MM-dd` string and calls
`onValueChange` with `Date | undefined`. `FormDateTimePickerField` takes a
`Date` or `null` and calls `onValueChange` with `Date | null`. Pass
`id={field.name}` to the select and date fields (the text field defaults to
it) so a field is addressable by name, for example by `focusFirstInvalid`
from `form/focus-first-invalid`, which focuses the first field with errors
when a submit fails. `FieldError`
accepts either `message` or pre-resolved `text`, and an `id` to point the
control's `aria-describedby` at. Every `form/*` field does that for you: the
error text (and `FormTextField`'s `description`) is the control's accessible
description. The date fields label their trigger with `aria-labelledby` (the
label, then the trigger) rather than `<label for>`, so the picked date is
part of its name.

Errors wait for the person. When `meta.isTouched` is `false`, a `form/*`
field hides its error text and invalid styling until the field is touched or
its `submitted` prop is set. Pass TanStack Form's `field.state.meta` as is
and this works on its own: TanStack marks every mounted field touched when
the form is submitted, so untouched fields show their errors then without
`submitted`. `submitted` is for form libraries that do not touch fields on
submit. Meta without `isTouched` shows errors as soon as they exist.
`showError={false}` always hides them. Every `form/*` field,
`FormSelectField` and both date fields included, takes `submitted` and
`showError`.

`FormControlField` gives a control the kit does not ship (a colour picker,
say) the same label, required marker, hint, error, ids, and error timing.
Use it rather than `Field` and `FieldLabel`, whose `gap-3` spacing does not
match the form fields. `children` is a function that receives the props to
spread on the control:

```tsx
<div className="grid grid-cols-2 items-start gap-3">
  <FormTextField field={amount} label="Amount" required />
  <FormControlField label="Currency" meta={currency.state.meta}>
    {(control) => (
      <Combobox
        {...control}
        options={options}
        value={value}
        onValueChange={set}
      />
    )}
  </FormControlField>
</div>
```

Each `form/*` field stacks label, hint, control, and error with `gap-1.5`.
The error sits below the control and takes no space until it shows, so use
`items-start` on a row of fields, as above, to keep the controls on one top
edge; the default `stretch` is fine for a single column.

Set `required` on a `form/*` field to mark its label with a visible `*`.
The marker is hidden from screen readers, which announce the control's own
`required` (`aria-required` on the select trigger). The date pickers are
buttons, which cannot be required, so their fields add "Required" to the
trigger's description instead. Outside the form adapters, `<Label required>`
draws the same marker; set `required` on the control yourself.

`DatePickerButton` is single-day by default. For a from/to range, set
`mode="range"`; `value` is `{ from, to }` (each side `Date` or `yyyy-MM-dd`)
and `onValueChange` receives `DateRange | undefined`. The trigger uses the same
form-control chrome as `Input` and `SelectTrigger`. Long picker values wrap
inside narrow triggers; ordinary one-line values stay 40px tall, and consumer
height classes still override that default. The range popover shows one
month below `md` and two months at `md+` unless `numberOfMonths` is set,
clamps to the viewport with collision padding and scroll, stays `w-auto` so
it does not collapse to the default popover width, and includes a Clear
action. In single mode, `clearable` adds the same Clear row (emits
`undefined`, closes the popover) and keeps the selected day on a second
click; without it, a second click on the selected day clears it. Pass
`side` to prefer a placement; Radix still flips on collision.
`minDate` and `maxDate` (each `Date` or `yyyy-MM-dd`) disable the days
outside them, on top of any `calendarProps.disabled`, and stop month paging
there unless `calendarProps` sets `startMonth` / `endMonth`. They limit the
calendar only; validate a value set some other way in your form.
The popover is a dialog named "Choose date" ("Choose dates" in range mode),
and focus moves to the selected day, or today, when it opens. Pass
`aria-labelledby` and `aria-describedby` to name and describe the trigger;
to keep the date in its name, list the label's id and then `${id}-value`,
the trigger text's id (a `<label for>` alone names the button by the label
only).
`FormDatePickerField` forwards `className` to that trigger.

`DateTimePickerButton` is the date-and-time control. `value` is a `Date` or
`null`; `onValueChange` receives `Date | null`. The trigger matches the same
form-control chrome. The popover is one month, a labelled Hour and Minute
pair (24-hour, stepped by `timeStep`, default 15), and Clear. Picking a day
keeps the popover open so the time can be set; the time selects stay
disabled until a day is chosen. The panel is `w-auto`, sized by the
calendar, and clamped to the viewport so it stays on-screen at 390px. Pass
`side` to prefer a placement. Like `DatePickerButton`, the popover is a
named dialog ("Choose date and time") that focuses the selected day or
today, and the trigger takes `aria-labelledby` and `aria-describedby`. `FormDateTimePickerField` forwards `className`
and `timeStep` to that control.

```tsx
import { DateTimePickerButton } from "atlas-react-kit/date-time-picker"

export function EventStarts({
  value,
  onValueChange,
}: {
  value: Date | null
  onValueChange: (date: Date | null) => void
}) {
  return (
    <DateTimePickerButton
      value={value}
      onValueChange={onValueChange}
      timeStep={15}
      placeholder="Pick a date and time"
    />
  )
}
```

```tsx
import { DatePickerButton, type DateRange } from "atlas-react-kit/date-picker"

export function ExportRange({
  value,
  onValueChange,
}: {
  value: DateRange | undefined
  onValueChange: (range: DateRange | undefined) => void
```

## Theme

```tsx
import { ThemeProvider } from "atlas-react-kit/theme-provider"

export function Providers({ children }: { children: React.ReactNode }) {
  return (
    <ThemeProvider storageKey="app-theme" enableShortcut>
      {children}
    </ThemeProvider>
  )
}
```

`ThemeProvider` is a client component and does not import Next.js. It stores the
choice under `atlas-theme` unless `storageKey` is set. The `d` dark/light toggle
is off by default; pass `enableShortcut` to turn it on, and give people a setting
to turn it off again, since a single-key shortcut can fire by accident (WCAG 2.1.4).

## App shell navigation

Pill links for top-level destinations (Calendar, Tasks, Settings). Pass
`active` from the route; the kit does not read the URL. Wrap a router link
with `asChild`, or use the optional Next adapter.

```tsx
import Link from "next/link"
import { NavLink } from "atlas-react-kit/nav-link"

export function AppNav({ pathname }: { pathname: string }) {
  return (
    <nav aria-label="App" className="flex items-center gap-1">
      <NavLink asChild active={pathname === "/calendar"}>
        <Link href="/calendar">Calendar</Link>
      </NavLink>
      <NavLink asChild active={pathname === "/tasks"}>
        <Link href="/tasks">Tasks</Link>
      </NavLink>
    </nav>
  )
}
```

```tsx
import { NavLink } from "atlas-react-kit/next/nav-link"

export function AppNav({ pathname }: { pathname: string }) {
  return (
    <nav aria-label="App" className="flex items-center gap-1">
      <NavLink href="/calendar" active={pathname === "/calendar"}>
        Calendar
      </NavLink>
      <NavLink href="/tasks" active={pathname === "/tasks"}>
        Tasks
      </NavLink>
    </nav>
  )
}
```

In-page view switches that still belong in the URL use `TabsNav`, not
`NavLink`; `Tabs` is for `TabsContent` panels that stay on one page.

## URL navigation in Next.js

```tsx
import { TabsNav } from "atlas-react-kit/tabs"
import { TabsNavLink } from "atlas-react-kit/next/tabs-nav-link"

export function ViewSwitcher({ view }: { view: string }) {
  return (
    <TabsNav aria-label="Items view">
      <TabsNavLink href="?view=list" active={view === "list"}>
        List
      </TabsNavLink>
      <TabsNavLink href="?view=board" active={view === "board"}>
        Board
      </TabsNavLink>
    </TabsNav>
  )
}
```

Outside Next, use `TabsNavLink` from `tabs`: a plain anchor with the same
chrome, `data-state`, and `aria-current="page"`, or `asChild` around your
router's link. `isNavActive` from `nav-link` works for the `active` check
here too.

```tsx
import { TabsNav, TabsNavLink } from "atlas-react-kit/tabs"

export function ViewSwitcher({ view }: { view: string }) {
  return (
    <TabsNav aria-label="Items view">
      {["list", "board"].map((item) => (
        <TabsNavLink key={item} href={`?view=${item}`} active={view === item}>
          {item}
        </TabsNavLink>
      ))}
    </TabsNav>
  )
}
```

Hook-driven controls and form handlers declare their client boundary; presentational
modules such as `button`, `badge`, `card`, `nav-link`, and `skeleton` can be composed from
React Server Components. Pass interactive callbacks from client components.
